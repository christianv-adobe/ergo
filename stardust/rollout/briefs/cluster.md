# Cluster unit brief (replica Phase 5 — sibling render + delivery for one template)

Your template's archetype is LIVE and gated. You render its siblings (migrate sibling tier, Path A′) and deliver them through the archetype's proven encoder (the archetype's blocks + content shape). Read `stardust/rollout/briefs/archetype.md` first: its Hard rules, Target, the chain steps 3–8 and the "Learned in earlier units" section all apply to you unchanged — with your page list instead of one page.

## Extra rules for clusters
- Another unit may be running at the same time on a DIFFERENT template. Only touch: your pages' content files, your sibling render inputs/outputs, and blocks that ONLY your template uses (named in your unit prompt). Shared blocks named in your unit prompt as "do not edit" are owned by the running unit: if one needs a change, solve it with content (an existing variant class) or append a line to `stardust/rollout/foundation-requests.md` (`- <unit> | block <name>: <what> | <evidence> | <templates>`) and ship without it.
- `git pull --rebase` before every commit/push; commit only your files.
- You may advance ONLY your own sibling slugs in stardust/state.json and only with `node stardust/scripts/stardust/state.mjs advance <slug…> --to <status> --skill migrate` if migrate.mjs requires a status to render them (never edit state.json by hand, never touch other slugs).

## Sibling steps (handoff contract § 1 — read `$P/replica/reference/handoff-contract.md` section `1. Migrate`)
1. Variance probe once for the template: `node stardust/scripts/replica/sibling-variance.mjs <archetype-live-url> <sibling-live-urls…> --probe <block>=<sel> … --width 1440` (archetype's own block selectors from its prototype). Save the JSON to `stardust/rollout/units/<unit>-variance.json`. Deltas → block VARIANT classes on the sibling's content, never per-page block forks.
2. Structural clone input per sibling: the archetype prototype was built by `node stardust/replica/build-prototype.mjs <slug>` from a content model `stardust/replica/content/<slug>.json` that the extractor scripts (`stardust/replica/extract-*-content.mjs`, see your unit prompt) produce from the capture `stardust/current/pages/<slug>.html` + `.json`. Produce each sibling's content model the same way, build `stardust/prototypes/<sibling>-proposed.html` (the encoder INPUT, never gated locally), then `node stardust/scripts/migrate/migrate.mjs render <siblings…> --archetype <sibling>=<archetype> … --canon-css stardust/prototypes/shared/canon.css` and `migrate.mjs modules <slug> <ids…>`. Where the clone flattens a section the archetype lacks, read the hydrated capture instead. Content verbatim (content-preservation rules): every heading, paragraph, CTA label+href, image+alt of the capture; log any deviation with `migrate.mjs deviation`.
3. Content-count acceptance per page: `node stardust/scripts/diff/content-diff.mjs <capture-or-live-url> <rendered-url> --profile generic --main <root>` → `looks-same 🔴 0 · nothing-lost 🟡 0` on the main root; record `migrate.mjs gate <slug> content-count --evidence "…"` and `content-fidelity`.
4. Encode each sibling into `content/<lowercase da path>.html` with the archetype's blocks, then the archetype brief's chain steps 4–8 for all your pages together (one paths file `stardust/rollout/units/<unit>.paths`, one batch ledger `stardust/deploy/ledger-<unit>.json`, `--concurrency 1`), gate-all `--only <your slugs>` at 1440 and 360 (a --state copy marking your pages deployed). Cap 3 fix rounds per page.
5. Coverage: `update-coverage.mjs <slug> --status deployed --url …` per page.
